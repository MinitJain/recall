# P3.16 Milestone Spec — Generalize `Bookmark` → `Item`

Grounded in the current schema (`client/prisma/schema.prisma`) and the current `POST /api/bookmarks` route (`client/src/app/api/bookmarks/route.ts`). Written to be precise enough for a weak/free model to execute step by step, not infer architecture.

## 1. Schema change (`prisma/schema.prisma`)

```prisma
enum ItemType {
  LINK
  NOTE
  PHOTO
}

enum SourceChannel {
  WEB
  EXTENSION
  BOOKMARKLET
  TELEGRAM
  WHATSAPP
}

model Item {
  id            String        @id @default(cuid())
  type          ItemType      @default(LINK)
  sourceChannel SourceChannel @default(WEB)

  url         String?       // required for LINK, null for NOTE/PHOTO
  title       String?
  description String?
  thumbnail   String?
  content     String?       // raw text, only for NOTE
  storageUrl  String?       // Supabase Storage path, only for PHOTO
  createdAt   DateTime      @default(now())

  userId String

  tags        Tag[]
  collections CollectionBookmark[]

  @@index([userId])
  @@map("Bookmark")   // keeps the existing Postgres table name — no data migration needed
}
```

**Why `@@map("Bookmark")`:** renaming the Prisma model but keeping `@@map` to the old table name means `npx prisma migrate dev` only **adds columns** (`type`, `sourceChannel`, `content`, `storageUrl`, all with defaults) — it does not rename or recreate the table, so existing rows survive untouched and get `type=LINK, sourceChannel=WEB` automatically via the column defaults. No manual backfill script needed.

`Tag` and `CollectionBookmark` keep their `bookmarkId` field name — renaming those too is optional cosmetic churn, not required for this milestone. Skip it.

## 2. Migration steps, in order

1. Edit `schema.prisma` as above
2. `cd client && npx prisma generate`
3. `npx prisma migrate dev --name generalize-item-model` (not `db push` — this milestone needs a real migration file since it's a structural change on production data, reviewable before applying)
4. Inspect the generated SQL in `prisma/migrations/.../migration.sql` before applying to prod — confirm it's only `ALTER TABLE ... ADD COLUMN` statements, no `DROP`
5. Apply to prod via the existing deploy flow

## 3. API contract

New route: `client/src/app/api/items/route.ts` — same logic as current `bookmarks/route.ts`, generalized:

```
POST /api/items
Body (LINK):  { "type": "LINK", "url": "https://..." }
Body (NOTE):  { "type": "NOTE", "content": "raw text" }
Body (PHOTO): { "type": "PHOTO", "storageUrl": "https://<supabase-storage-path>" }

Response 201: { id, type, sourceChannel, url, title, description, thumbnail, content, storageUrl, createdAt, aiTagsFailed }
```

`sourceChannel` is set server-side from an auth context (extension token vs bot webhook vs web), never trusted from the client body.

**Backward compatibility:** keep `client/src/app/api/bookmarks/route.ts` as a thin alias — `POST` forces `type: "LINK"` and forwards to the same underlying function `/api/items` uses. The shipped Chrome extension keeps working unmodified. Mark `/api/bookmarks` as deprecated in a comment, don't delete it this milestone.

## 4. Validation rules per type

- **LINK**: `url` required, existing SSRF/protocol checks unchanged
- **NOTE**: `content` required, non-empty, max length (pick one, e.g. 10,000 chars, and enforce it)
- **PHOTO**: `storageUrl` required, must be a path the authenticated user actually owns in Supabase Storage — don't trust an arbitrary URL, validate it's under that user's storage folder

## 5. Definition of done

- [ ] `GET /api/items` returns existing bookmarks unchanged, now with `type: "LINK"`, `sourceChannel: "WEB"`
- [ ] `POST /api/bookmarks` (old route) still works, extension untouched
- [ ] `POST /api/items` accepts all three types with the validation above
- [ ] Migration SQL reviewed, contains no `DROP`/`RENAME`
- [ ] `npx tsc --noEmit` passes
